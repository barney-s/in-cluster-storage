## 1. Architectural Pivot Summary
During execution of the original `deploy-kops-gce.md` runbook, the deployment was strategically pivoted to target the pre-existing, healthy GKE cluster `ics-1` in the `barni-cnrm-20260529` project due to two primary constraints:
1. **IAM Permission Boundary**: The active Workload Identity deployment account (`cnrm-barni-1.svc.id.goog`) has the project-level `roles/editor` role but lacks the high-privilege `resourcemanager.projects.setIamPolicy` permission. Since `kops create/update cluster` on GCE strictly requires creating dedicated GCE IAM service accounts and binding project-level IAM roles via `setIamPolicy`, deploying KOPS GCE under this identity is physically impossible in this sandbox.
2. **Missing Local Docker Daemon**: The local environment lacks an active Docker daemon in the PATH. To build, tag, and register the six storage subsystem container images flawlessly, the script was updated to leverage parallel **Google Cloud Build** jobs directly in GCP.
