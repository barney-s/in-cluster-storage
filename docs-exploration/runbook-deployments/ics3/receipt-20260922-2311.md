## What Executed

We executed the KOPS on GCE deployment scenario (deployment instance `ics3`) using automated scripts and resolved permission boundaries and YAML parsing constraints.

### Attempt Log

- **Attempt 1: GCS State Store Read Failure (HTTP 412/403)**
  - *Symptom*: When `kops create cluster` executed, it returned:
    `googleapi: got HTTP response code 412 with body: The type of authentication token used for this request requires that Uniform Bucket Level Access be enabled.` and `403 Forbidden` because the active identity lacked storage permissions.
  - *Cause*: In this federated GCP project environment, state GCS buckets must have Uniform Bucket Level Access (UBLA) enabled. Furthermore, when UBLA is enabled on GCS, legacy ACL permissions (such as `roles/storage.legacyBucketOwner`) are ignored, meaning the project Owner active credential had no effective permissions on the newly created bucket.
  - *Fix*: Modified `deploy.sh` to enable `--uniform-bucket-level-access` upon bucket creation and dynamically query and bind the `roles/storage.admin` role to the active Workload Identity principal.

- **Attempt 2: Kubernetes YAML Syntax Failure in CAS CSI Driver**
  - *Symptom*: YAML syntax error during CAS deployment:
    `error: error parsing STDIN: error converting YAML to JSON: yaml: line 19: found unknown escape character`
  - *Cause*: The script used literal `<<'EOF'` heredoc format. Inside this literal block, environment variables like `$(ADDRESS)`, `$(DRIVER_REG_SOCK_PATH)`, and `$(NODE_ID)` were backslash-escaped (e.g., `\$(ADDRESS)`). Since single-quoted literal heredocs do not evaluate bash expansions, the backslashes remained literal in the output, which is invalid syntax inside double quotes in YAML.
  - *Fix*: Removed the backslash escapes of variable references inside the CAS heredoc in `deploy.sh`.

- **Attempt 3: Subsystem Pod Authorization and Image Pull Failure (HTTP 403 / ImagePullBackOff)**
  - *Symptom*: Pods in `kube-agentfs-system` and `kube-objectfs-system` remained in `ImagePullBackOff` status. Pod description logs revealed a 403 Forbidden on pull.
  - *Cause*: KOPS-managed GCE nodes do not operate under the GCP default Compute service account. Instead, KOPS provisions its own dedicated node service accounts:
    - `node-ics3-k8s-local@barni-cnrm-20260529.iam.gserviceaccount.com`
    - `control-plane-ics3-k8s-local@barni-cnrm-20260529.iam.gserviceaccount.com`
    These dedicated service accounts lacked private Artifact Registry reader permissions.
  - *Fix*: Updated Section 5 of `deploy.sh` to dynamically grant `roles/artifactregistry.reader` to both the default Compute service account and the dedicated KOPS worker and control-plane service accounts. Deleted the pods to trigger a fresh pull, resulting in immediate healthy startup of all workloads.
